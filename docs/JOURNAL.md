### [2026-07-27] SESSION — FIX prod critique : schéma Supabase drastiquement désynchronisé de schema.prisma
**Contexte :** découvert en testant le flush ci-dessus — `stockClosure.deleteMany()` plantait en 500 avec "table StockClosure does not exist". En creusant (`information_schema.columns` sur toute la prod), la dérive était bien plus large qu'un cas isolé.
**Cause racine (diagnostic confirmé par l'utilisateur) :** `git push` ne déploie que le code applicatif (Vercel) — jamais le schéma Prisma vers Supabase. Ce sandbox ne peut pas non plus lancer `prisma db push`/`migrate` directement (`DATABASE_URL` réelle systématiquement scrubée dès récupération). Le seul filet de sécurité était la mémoire humaine/agent pour rattraper chaque écart après coup via `supabase db query --linked` — raté plusieurs fois d'affilée (POS, `flow.read`, `BomStock.stockId`, et maintenant tout le module Boutique/Produits).
**Ampleur réelle constatée :**
- 3 tables entières absentes : `TenantVatRate`, `ProductChannelStock`, `StockClosure` (+ enums `StockChannel`, `ClosureReason`).
- `Product` tournait encore sur le **schéma pré-BOM** : colonnes obsolètes `recipeId`/`vatRate` (enum)/`stockType`/`stockQuantity` présentes, colonnes actuelles `bomSheetId`/`vatRateId`/`marginTargetFactor`/`isPerishable` absentes.
- `OrderItem.vatRate` (ancien enum `VatRate`) jamais renommé en `vatRatePercent` (Decimal).
- `PosSaleItem.productionId`/`unitCost` jamais poussés (rework vente à la demande du 2026-07-26).
- `Recipe.productId` jamais poussé.
- `BomStock.stockId` jamais poussé (règle #40, pourtant journalisée comme faite le jour même).
**Fix :** vérifié d'abord qu'aucune ligne dépendante n'existait en prod sur les 3 tenants (`Product`/`OrderItem`/`PosSaleItem` à 0 ligne) avant toute action destructive. `npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` généré sans connexion DB pour obtenir le DDL exact cible, puis `scripts/prod-schema-catchup-2026-07-27.sql` (transaction unique `BEGIN`/`COMMIT`, `DROP TABLE "Product" CASCADE` + recréation propre vu qu'elle était vide et incompatible, `ADD COLUMN`/`ADD CONSTRAINT` pour le reste) appliqué via `supabase db query --linked`. Vérifié colonne par colonne après coup que les 6 tables concernées correspondent exactement au schéma actuel.
**Règle retenue :** toute session qui modifie `schema.prisma` doit se terminer par soit (a) un vrai `prisma db push`/`migrate deploy` lancé par l'utilisateur depuis sa propre machine (la seule `DATABASE_URL` non scrubée), soit (b) un script SQL de rattrapage généré via `prisma migrate diff --from-empty --to-schema-datamodel` et appliqué via `supabase db query --linked` — jamais suppose que le déploiement Vercel a aussi mis à jour la DB.
